# 记忆写入纪律与 Obsidian 分工

这是第一阶段的使用约定和待验证假设，不代表已经检查或修改用户的 Obsidian vault。
Codex 已提供会话钩子；WorkBuddy 和 DeepSeek Harness 当前依靠项目/工具指令触发，强度不同。

## 各自存什么

Obsidian 保留用户阅读、整理和维护的完整笔记、日记、知识资料，是这些文档的原始来源。
Personal Memory 保存供不同客户端快速调用的简短个人状态、已确认偏好、项目进度、决策和事件摘要。
从笔记提炼的记忆必须在 source 中标注 vault 标识、相对文件路径、标题或段落，以及提炼时间；必要时附原文文件哈希。
用户只需维护原始笔记；提炼记录发生冲突时先查原文，不能以过期摘要覆盖原文。
对话中首次确认的事实可直接写记忆，source 标注对话引用；值得长期展开的内容再形成 Obsidian 笔记。

第一版不做双向自动同步、不把整个 vault 复制进数据库。数据库中的文件路径只是来源引用，不会在检索时自动读取 Obsidian。
归档 Markdown 用于迁移/备份，不等于 Obsidian 自动同步；手动编辑归档的可读区不会改变 canonical JSON。

## 什么该记

记录稳定偏好、用户明确确认的个人事实、完成的重要事件、带理由的决策，以及项目里程碑/当前阻塞/下一步。
临时聊天、未验证的推断、重复内容、密码与访问令牌不进入长期记忆。
一条记忆表达一件可独立更新的事，正文尽量短，必须标注可追溯来源。当前 API 允许 source 为空以便迁移，但日常使用应填写。

## 双模式写入

| 触发时机 | 负责方 | 行为 |
| --- | --- | --- |
| 用户说“记住/记录/以后按这个/纠正/忘记” | 当前客户端助手 | **指定写入**：立即查重并 store/update/supersede/forget；返回成功结果 |
| 普通聊天出现稳定偏好、确认事实或长期决定 | 当前客户端助手 | **自动写入**：无需触发词，模型判断后提炼少量原子记录 |
| 项目完成里程碑、做出决策或出现新阻塞 | 正在执行任务的助手 | **自动写入**：在当轮或交接前保存进展，不存整段工具输出 |
| 用户说“收尾/交接/总结” | 当前客户端助手 | 核对本次变化，保存进展、阻塞和下一步；最终说明哪些已实际写入 |
| 导入某篇 Obsidian 笔记 | 用户指定文件，助手处理 | 第一阶段手动提炼/导入，保留出处，不自行扫描整个 vault |
| 开始新会话 | 当前客户端助手 | context 读取对应 project/domain + global，必要时 search，再按来源核验 |
| 用户提到“之前/还记得/继续/已有方案/我的偏好” | 当前客户端助手 | 回答前先检索相关记忆，再结合来源作答 |

读取纪律（三端统一，v0.2）：新会话处理有持续背景的任务先调用 memory_context；提到历史背景时
回答前检索；项目任务使用约定 scope，不知道标识时先读 global 再结合项目文档确认，不自行创造；
同一会话已有且未变化的背景可以复用，话题切换、用户纠正或工具报告修订时重新检索；简单翻译、
计算等无历史依赖请求可以跳过；MCP 不可用时正常处理独立工作，需要历史才能回答的部分明确说明
无法核实。建议启动参数 `view="compact"`、`max_chars=6000`、`limit=8`。

规则注入只是触发读取要求，不等于已经调用 MCP；只有工具返回内容才算读到。

MCP 后端看不到聊天内容，不能自己判断应记什么；自动写入由客户端的模型规则或生命周期钩子触发。
Codex 的 UserPromptSubmit 钩子注入规则，Stop 钩子在每轮结束前强制再检查一次；第二次停止通过
stop_hook_active 放行，避免循环。它会增加一次结束前模型步骤，因此比仅靠提示词更可靠，也有少量
时延/用量成本。WorkBuddy 和 DeepSeek Harness 目前是“模型规则自动”，不是硬钩子保证。

所有写入先查目标 scope；服务端还会拦截同 scope/type/title/content 的当前有效精确重复。
source.trigger 必须尽量标记 explicit 或 autonomous。自动写入通常每个有意义的轮次最多 1-3 条；
没有耐久信息时不写，避免把数据库变成聊天流水账。
“准备记录”和“已写入”必须区分；只有工具返回成功才能声称保存。失败应在交接中说明。
会话被强制关闭、客户端崩溃或 MCP 不可用时，仍可能漏写；后续可增加待审查队列，而不是让后端
直接抓取全部聊天。

## 第一周如何验收（手动试用计划）

1. 将 Codex、WorkBuddy 与 DeepSeek Harness 指向相同的数据库绝对路径，分别用 status 确认。
2. 在一个客户端写入一条明确标识的测试记忆，在另一个全新会话检索，再软删除该测试记录。
3. 实际任务只保存少量有用记录。每天/每次收尾核对本次该记录的变化是否已写入，避免只测试空库服务可用。
4. 用真实问题验证：“用户有哪些已确认偏好”“某个项目当前做到哪”“为什么做这个决定”。没有来源的答案应明确未知。
5. 手动记录 query、范围、返回 ID、哪些结果有用/遗漏；积累几十条后再判断 embedding 或排序改进是否必要。

当前服务不记录查询日志；避免让人误以为已经有自动评估数据。可先用同目录 query-evaluation.csv 手工记录；自动检索日志属于后续可独立加入的改动。
当前 FTS5 结果按 BM25、重要度、置信度和时间依次排序；v0.2 在传入 `query_variants` 时增加
`score = Σ 1/(60+rank)` 的 RRF 融合，未传时排序与旧版一致。融合是词法关键词合并，不是向量检索。
第二套后端不会自行解决“谁写”的问题；只有当前方案在真实客户端试用中遇到具体问题，再决定是否安装 Engram 对照。

## 写入与更新纪律（v0.2 明确）

- 一条记忆尽量只表达一件可独立变化的事；稳定偏好、当前任职、基金配置、关注名单分开保存。
- 关注标的不等于持仓，计划不等于已完成；历史事件保留时间背景，不当作当前状态。
- 事实变化用 supersedes；同一事实的纠错用 memory_history + expected_revision + memory_update。
- 精确重复直接跳过；不要为了去重而使用 supersedes。
- 助手推断不能升级为用户已确认事实；confidence 是来源与写入者的判断，不是模型算出的概率。
- 发现相互不一致的记录时展示来源、时间和适用环境；禁止仅凭“更新时间更晚”自动覆盖旧记录。

正式库现有复合条目本次只生成整理建议，不批量拆分或删除；自动整理器留给后续版本。
