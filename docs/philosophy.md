# 设计理念

这篇说明项目为什么这样设计。功能与命令见根目录 `README.md`；这里记录长期取舍。

## 记忆不只是存储问题

“给 AI 加记忆”表面上像是选择一个数据库，真正困难的是：

1. **什么时候该写。** 临时想法、推测和一次性状态不应自动变成长期事实。
2. **写进去的是否可靠。** 转述、计划和已完成事项必须区分，来源和可信度不能被摘要抹掉。
3. **没找到时如何回答。** 词法检索没有命中，不等于用户从未记录；模型不能据此编造记忆。

项目围绕这三点设计，而不是单纯追求更多功能或更高召回率。

## 确定性优先

后端不调用 LLM 判断检索结果，也不自动摘要、合并或改写记忆。模型负责从当前问题提取关键词、
核对候选是否真正回答问题，并通过 MCP 发起显式读写；后端负责可复现的校验、过滤、排序和修订。

这样做有三个直接收益：

- 同样的数据和查询得到稳定结果，问题可以复现；
- 每一步规则和数据都能检查，错误可以定位；
- 服务可以离线运行，不依赖某个模型或云服务。

代价是同义词、跨语言表达和改写可能漏检。项目选择把这一限制明确暴露，而不是用不透明的自动
扩展掩盖它。

## 可诊断比强行召回更重要

`memory_search` 与 `memory_context` 都返回 `retrieval` 诊断。严格检索常见结果包括：

| reason | 含义 |
| --- | --- |
| `empty_scope` | 范围和有效期过滤后没有活动记录 |
| `no_lexical_match` | 范围内有记录，但关键词没有词法命中 |
| `offset_beyond_pool` | 候选存在，但当前分页越过候选池 |
| `matched` | 当前检索策略得到候选 |

`search_mode="auto"` 的宽松回退成功时使用 `relaxed_match`，记录带
`match_quality="relaxed"`。宽松结果只是候选，必须检查正文是否直接回答问题；主题相关不等于找到了
所问的具体事实。

## 时间是一等公民

事实会变化，因此记录带有效期 `[valid_from, valid_to)`：

- 世界发生变化时，新建记录并用 `supersedes` 指向旧记录；旧记录被原子关闭但保留历史。
- 原记录内容写错时，使用带 `expected_revision` 的 `memory_update` 纠正并留下修订快照。

一个表示事实变化，一个表示记载纠错。两者分开，历史才可信。

## 复杂度本身也是风险

个人记忆底座需要长期信任。代码、规则和自动行为越多，越难回答“它到底存了什么、为何返回这条、
什么时候改过”。项目因此优先保持小型、可读和可替换；只有真实使用证据表明确有需要时，才增加新的
索引或自动化层。

## 明确不做的事

| 当前不做 | 原因 | 何时重新评估 |
| --- | --- | --- |
| 默认向量检索 | 引入模型依赖、索引版本和不可复现因素 | 词面不匹配成为主要失败来源且有评测证据 |
| 多租户、密级和 ACL | 当前是单机单人服务，scope 只是分类 | 多人共享服务或出现真实授权边界 |
| 自动整合与自动遗忘 | 会在后台改写用户事实 | 记忆规模大到人工修订无法维持 |
| 自主摄取聊天 | 服务不能也不应在后台读取会话 | 客户端提供明确、可审计的事件与授权 |
| 世界模型或自我演化 | 超出事实记忆范围，难以验证 | 应由另一个有独立评测的系统承担 |

## 一句话

> 记忆系统的价值不只在于记住多少，也在于没找到时能明确告诉你：这次没有可靠命中。
